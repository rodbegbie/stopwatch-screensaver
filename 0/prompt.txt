  #### Important (Should Fix)
  1. **Projecting caps on a 3+ point polyline are one pixel too long for odd widths.**
     - Where: `stroke.c:144-147`. `segment_quad` adds the "cover the vertex pixel" 0.5 and then `half` as well.
     - Evidence: `XDrawLines` with three collinear points, `CapProjecting`, widths 3, 5, 7 and up to 41 gives a different picture from the single `XDrawLine`, for all four directions (720 of 4320 cases differ).
     - Which is right: the integer path (`ext = w/2`) matches the X rule that a projecting cap extends w/2 past the endpoint. The float path is the wrong one.
     - Reach: it also hits any thick `XDrawArc` or `XDrawRectangle` that has projecting caps.
     - Slanted lines: a single slanted segment with odd width and projecting caps is 0.5 px too long, from the same cause.
     - Why the tests missed it: `test_polyline_with_two_points_equals_a_segment` compares code with itself, because m==2 delegates to `stroke_segment`. `test_collinear_points_draw_the_same_as_one_segment` uses butt caps only.
     - Fix: for `CapProjecting`, use `e = half + max(0, ±pixel_along)` rather than `max(0.5, ...) + half`. For odd widths that gives `half`, and for even widths `half + 0.5`. Then add a projecting-cap case to the collinear test.
  
  2. **`clip_to_canvas` (double) runs for every slanted wide segment, not only for far-out ends.**
     - Where: `slanted()` at `stroke.c:162` calls it unconditionally. About 30 double operations run per segment, in software on the S3, which has a single-precision-only FPU.
     - Likely cost: it is multiplied by every segment of a thick arc (up to 1024 per arc).
     - Fix: skip the clip when all four coordinates satisfy `|v| < 1<<20`. Floats are exact enough there, and the result is identical.
     - Related: `disc()` goes through `canvas_fill_ellipse`, which also uses double (that code is pre-existing). Round joins on arc polylines therefore add double work per vertex, up to about 733 vertices for a radius-233 circle. This is unmeasured, so please check fps on the device before and after if round or miter arcs are meant to run every frame.
  
  #### Minor (Nice to Have)
  3. **Precision loss in unclipped polylines at extreme coordinates.**
     - Where: `stroke_polyline` hands float vertices straight to `segment_quad` with no clip, unlike `slanted()`.
     - Evidence: `XDrawLines` with points (-INT_MAX,-INT_MAX), (0,0), (INT_MAX,INT_MAX-1000) at w=3 drew 6 pixels. The same line as a single `XDrawLine`, or with 1e6 coordinates, draws the expected 2324. It is bounded, with no hang and no overflow, but the picture is wrong.
     - Fix: clip each segment first, or fall back to a double path when |coordinate| > 2^20.
  4. **Long axis-aligned segments (over about 4096 px) can be one row thin.** `sqrtf(dx*dx)` is not exactly dx, so `uy` or `ux` is not exactly 1 and the ties shift. This only affects polylines, since single segments take the integer path.
  5. **Float-to-int casts in `arc.c:37-38`.** `lrintf` of a float beyond int range is unspecified. On the device `long` is 32 bits, so this applies to arcs with w or h near 2^32 or large x. It does not crash, it only produces garbage geometry, and no NaN can occur. Clamp before the cast.
  6. **Arcs over about 128 px diameter use two mallocs per `XDrawArc` call** (the n>64 stack fallback in `xshim.c` and `stroke_polyline`). That is fine on PSRAM, but it is per frame. A larger stack buffer of about 2 KB would avoid it.
  7. **`MAX_PIXMAP_PIXELS` is 4M (8 MB)**, bigger than the 8 MB PSRAM it is meant to protect. `malloc` fails safely and the function returns `None`, so it is harmless; the comment is just generous.
  8. **Thick arcs are plain polylines with the GC's join style.** Miter joins on 2-px-spaced rounded points can add up to about 0.4 half-width bumps on the outer edge. The w=4 render looked fine.
