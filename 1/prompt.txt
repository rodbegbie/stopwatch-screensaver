That includes `glColor` with colour material on, because `glopColor` calls `glopMaterial`. `GL_LAZY_SHADE` is defined in `glshim_prof.h`, which reaches `zgl.h` through `tinygl_single.h` before the macros are used, so every TinyGL file sees the same setting.
  - **Additive blend.** `TGL_BLEND_ADDS` matches TinyGL's own switch statements: any factor other than `ONE_MINUS_*_COLOR` or `ZERO` falls into `default:` and is treated as ONE. So the fast path changes only the colour arithmetic, not which blends count as additive. No frame hash other than StonerView's moved.

  ### Important
  
  1. **Re-opening a context throws away the requested scale** (`firmware/src/glshim/glshim.c:229-232`, with the reset at `:220`). `glshim_open` calls `glshim_close()` first, and close sets `g_scale = g_next_scale = 1` whenever a context is open. If `glshim_set_render_scale(2)` is called while a context is still open, the open that follows quietly runs at scale 1. The test suite already exercises opening while open (`test_opening_twice_replaces_the_context_without_leaking`).
     - Scenario: a HYPNOWHEEL_HALF build hits any init path that reaches `init_GL` before the previous context was released. It runs at full size and about 2 fps, and nothing reports it.
     - Fix: have `glshim_open` keep `g_next_scale` across its own internal close, then reset it after it has been read. Add a test for "set 2, open, set 2, open again".
  2. **A failed open leaves the scale set for the next GL hack** (same lines). `glshim_close` returns early when `g_zb` is NULL. If `ZB_open` fails, or the hack's init fails between `glshim_set_render_scale(2)` and `glshim_open`, both `g_next_scale` and `g_scale` stay at 2.
     - Scenario: Hypnowheel's init fails on an out-of-memory error. The next GL hack in the rotation (say Gears) opens at half resolution, and its `glViewport` is halved too.
     - Fix: reset both values on the early-return path of `glshim_open`, or read-and-clear `g_next_scale` at the top of open.
     - Today this only affects builds with `-DHYPNOWHEEL_HALF`.
  
  ### Minor
  
  3. **`memBench` reads and writes past the canvas** (`firmware/src/main.cpp`, `memWalk(psram, 32, kSize, kSize)` and the `colRead` loop). The column walk reaches index `465*466 + 31*16 = 217186`, but the canvas holds 217156 pixels, so it overruns by 30 pixels (60 bytes) into the next PSRAM allocation or heap metadata. Each value is XORed twice, so nothing is left changed, but it is still out of bounds. Fix: limit `x*16` to `kSize`. This is only built with GL_PROFILE.
  4. **`hacks/hypnowheel_single_gl.c` is now compiled in every environment.** No `build_src_filter` excludes it (only `hypnowheel_gl.c` is excluded), so every build carries Hypnowheel's sources and compile time even without `HYPNOWHEEL_PROBE`. It is probably dropped at link time unless `HYPNOWHEEL_HALF` adds its constructor.
  5. **Every flush walks all `POLYGON_MAX_VERTEX` slots** (`gl_shade_pending_all`). With colour material on and a `glColor` per vertex, that is one full walk per vertex. It also shades stale vertices left pending from earlier primitives, using the current matrix. That is wasted work but harmless, since those vertices are never drawn.
  6. **Rounding in `glshim_Viewport` at scale 2.** Dividing a negative or odd `x`/`y` truncates toward zero, and an odd canvas size would leave the last row and column stale. Neither affects the square 466 canvas.
  7. **On the host, `glshim_prof_now` cuts nanoseconds to 32 bits.** The difference stays correct while a single scope lasts under 4.29 s, which is fine, but worth knowing if someone profiles a slow hack on the host.
